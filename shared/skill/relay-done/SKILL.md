# Relay · 收棒

> Installation reference source. Do not copy this file verbatim. The installation model must adapt the explicit trigger, stable launcher invocation, local client format, and every placeholder to confirmed local facts.

Close only a phase whose declared outcome and evidence are complete. Explicit invocation authorizes the independent Relay store update/archive only, never project commit/push.

写入参数 `--model <current-model>` 使用当前客户端提供的实际模型稳定 ID，不使用带空格的显示名或猜测值；`--client` 使用已确认的稳定作者身份。两者的字符、长度与取值要求见[统一安装说明](../../command/relay/README.md)。

## Permission handling

- Treat the explicit entry invocation as one authorization for its complete Relay CLI, independent-store, and request-draft workflow. Never ask for approval per Relay subcommand or draft file.
- Use the host's active permissions first. Do not preemptively request elevated or full-access execution. `--help` and read-only `status` never justify proactive escalation.
- If the host actually denies a required Relay operation, stop repeated one-command requests and ask for one scoped Relay permission profile or authorization covering the stable launcher, Relay work directory, and configured remote.
- In full-access/no-approval mode, omit all escalation metadata. A permission change applies only after the current call ends and the execution environment refreshes.
- Never widen Relay authorization to project edits, project commit/push, setup, dependency installation, or unrelated configuration.

## Workflow

1. Require `relay` and run `relay status`. If the CLI cannot be launched, `status` returns an error, or `configured=false`, stop. In an otherwise successful response, `installation.source_status.state=unavailable` means Relay source-version evidence is unavailable in this repository; that field alone does not block the daily workflow. It does not prove the installed rules are current or override installation errors and stale/dirty guards below.
2. Use only an id and expected revision remembered after the installed Relay handoff entry or a confirmed installed Relay load entry. Without a reliable pointer, show `relay list` only for orientation and stop: the user **must run the installed Relay load entry first**.
3. Run `relay load --relay-id <internal-relay-id>` first. Require the returned revision to equal the pointer and reread phase outcome, phase completion criteria, `phase_completion`, **未解决 P0**, deviations, active decisions, and authority. Require `phase_completion.alignment_complete: true`; never treat legacy unknown/inferred status as `met`. `delta.criteria_changes` already contains each complete receipt for the loaded revision. For another current-format revision's suspicious action, authorization, or reason, call `relay recall --relay-id <source-id> --revision <source-revision> --criteria-ordinal <ordinal>` before closure; `--criteria-id <C-NNN>` is legacy-only compatibility. If `warnings` contains `installation_stale` or `installation_source_dirty`, stop before archival and report the required adapter reinstall or Relay-source cleanup; do not complete the phase under unverified local rules.
4. Re-check the actual worktree and fresh test/build evidence. Do not close merely because `next_step.done_when`, an internal batch, test gate, or ordinary review is complete. Declare every `phase.done_when_status` entry. Refuse any `pending`; preserve the reason for every `partial` / `unverifiable` result and never rewrite it as `met`. Also refuse for unresolved P0, unapproved deviation, stale revision, missing evidence, in-progress work, or unresolved authority.
5. Run `relay draft create --operation done --relay-id <internal-relay-id>`, take only `result.path` as `<internal-file>`, and register finally cleanup. The contextual draft carries the target and current snapshot. Rewrite current final truth with statuses positionally aligned to `phase.done_when`; preserve active decisions, evidence, future-stage P1/P2, and references, and list all still-active IDs in `changes.active_decision_ids`. Never append a closing log.
6. Keep predecessor unchanged. Phase outcome, `phase.done_when`, invariants, and non-goals are protected, and **Text equality is exact**: suffixes, exceptions, and “not applicable” notes are changes. Declare every replacement in `changes.criteria`. Use `strengthened` with the exact old text, exact replacement, reason, and `authorized_by: null` only for a genuine tightening of phase outcome, done criteria, or invariants. Use `removed`, `weakened`, or `merged_into` only with explicit user authorization. Declare every new list item with `added`; positive criteria use `authorized_by: null`, while **Adding `design.non_goals` shrinks scope** and requires explicit user authorization. Never use `strengthened` for a non-goal. On `criteria_transition_required`, restore the exact prior text or ask the user—never lower the acceptance line to make `done` pass. Decision removal separately requires an explicit lifecycle transition in `changes.decisions`; omission is not retirement.
7. Run `relay validate --request <internal-file>`, then `relay done --request <internal-file> --client <WRITER_IDENTITY> --model <current-model>`. Relay id and expected revision already live in the request target; never append them to the command. `<WRITER_IDENTITY>` is an installation placeholder, never a literal runtime value. The installation model must replace every occurrence with the user-confirmed stable writer identity; never substitute the host adapter name such as `codex` or `claude-code`.
8. The CLI moves authoritative canonical JSON and its derived Markdown export as one logical record. Before commit, failure restores the full active pair. Markdown drift is a non-blocking `document_export` diagnostic on load; canonical remains the source of truth. On `sync_error` with `details.local_committed=true`, retain returned done revision/path/canonical_path and report local closure without remote sync; never retry the old revision.
9. In finally semantics run `relay draft cleanup --path <internal-file>` on **every exit path**. Never move/delete/edit the formal pair or use stash, reset, merge, rebase, or force push. On synchronized success report phase outcome, final revision, both archive paths, and clear the pointer.
10. If the user has already defined the next phase, do not archive with standalone `done`; use the installed handoff entry's **successor transaction** so one CAS archives this phase and creates the next without user-copied prose or a predecessor id. Use standalone closure only when no successor is currently defined. An internal batch/review boundary is not, by itself, permission to create a successor — **only the user opens a phase.** You may recommend one, but the successor request requires their verbatim `authorization`, so a self-authorized phase cannot be written.
