# Relay · 交棒

> Installation reference source. Do not copy this file verbatim. The installation model must adapt the explicit trigger, stable launcher invocation, local client format, and every placeholder to confirmed local facts.

Save one bounded current-truth snapshot for a user-directed model handoff. Explicit invocation authorizes request-draft operations and the independent Relay store only, never project commit/push.

写入参数 `--model <current-model>` 使用当前客户端提供的实际模型稳定 ID，不使用带空格的显示名或猜测值；`--client` 使用已确认的稳定作者身份。两者的字符、长度与取值要求见[统一安装说明](../../command/relay/README.md)。

## Permission handling

- Treat the explicit entry invocation as one authorization for its complete Relay CLI, independent-store, and request-draft workflow. Never ask for approval per Relay subcommand or draft file.
- Use the host's active permissions first. Do not preemptively request elevated or full-access execution. `--help` and read-only `status` never justify proactive escalation.
- If the host actually denies a required Relay operation, stop repeated one-command requests and ask for one scoped Relay permission profile or authorization covering the stable launcher, Relay work directory, and configured remote.
- In full-access/no-approval mode, omit all escalation metadata. A permission change applies only after the current call ends and the execution environment refreshes.
- Never widen Relay authorization to project edits, project commit/push, setup, dependency installation, or unrelated configuration.

## Workflow

1. Require `relay` and run `relay status`. If the CLI cannot be launched, `status` returns an error, or `configured=false`, stop; do not install, create a remote, or change user configuration. In an otherwise successful response, `installation.source_status.state=unavailable` means Relay source-version evidence is unavailable in this repository; that field alone does not block the daily workflow. It does not prove the installed rules are current or override installation errors and stale/dirty guards below.
2. Update only a relay id and expected revision created by this conversation or obtained through a confirmed installed Relay load entry. Without them, use `relay list` only for orientation. **Never update from `relay list` alone** and never infer the newest revision.
3. **The user alone decides whether, when, and to whom the baton is passed. The user defines phase boundaries.** Honor every explicit handoff request. Never reject, delay, or question a handoff because the phase seems too small, unfinished, or inefficient. Relay records the baton; it does not choose or invoke the next model.
4. An internal batch boundary, test gate, ordinary review, or execution gate is not an automatic handoff or successor boundary chosen by the model. If the user chooses to hand off at one of those points, honor it. If the user requests only a mid-phase model switch and has not declared a new phase, update that same Relay instead of inventing a micro-phase.
5. Choose the internal path from the user's stated phase boundary, never from a changed `phase.name`: update the reliable active pointer for a mid-phase handoff; when the user has defined the next phase and the current phase satisfies every closure gate, use the successor transaction. **Opening a new phase is the user's call, never the model's.** You may recommend a successor, but without the user's explicit agreement the only available path is `pass` on the same baton. The successor request requires a non-empty `authorization` quoting the user verbatim; the CLI rejects an empty or template value, so a phase you opened on your own cannot be written at all. It consumes the conversation's reliable active id/revision, so the user never copies prose, selects a predecessor id, or supplies a second set of parameters. successor 前先用可靠指针运行 `relay load --relay-id <internal-relay-id>` 并核对 revision；若 warnings 含 `installation_stale` 或 `installation_source_dirty`，在归档旧阶段前停止并报告所需的适配器重装或源码核对，与独立收棒使用相同条件。
6. Run `relay draft create --operation create` for a root request, `relay draft create --operation update --relay-id <internal-relay-id>` for a same-phase update, and `relay draft create --operation successor --relay-id <internal-relay-id>` for a phase advance. The contextual draft writes the reliable relay id, expected revision, current snapshot, and decision-confirmation fields into the request envelope. Use only `result.path` as `<internal-file>`, register finally cleanup immediately, and never defer target parameters to the write command.
7. For a same-phase update, fill the complete structured request. Preserve:
   - final task outcome;
   - current **phase outcome**, phase completion criteria, and the positionally aligned `phase.done_when_status`;
   - non-goals, invariants, priorities, authority, evidence, P0/P1/P2, deviations, references;
   - `authority.must_not`: what the model **receiving this baton** may not do, written in its second person. This is a per-baton boundary, not a phase contract — rewrite it for every handoff and use `[]` when the next holder has no extra restriction. A limit that belongs to the current holder alone (“this leg only audits, it does not fix”) goes here, never in `design.non_goals`: a non-goal is G1-protected and inherited, so putting a role boundary there locks the next holder out of the very work you are handing them and forces a needless new phase.
   - a semantic first action with project-relative cwd/read/modify paths, command hint, expected result, done condition, and failure branch. For a read-only action, keep `modify` empty instead of inventing a “do not modify” target.
   Each phase status is `pending`, `met`, `partial`, or `unverifiable`. `partial` and `unverifiable` require a reason; neither the writer nor CLI may infer `met`.
   `phase.done_when` defines completion of the whole phase. `next_step.done_when` closes only the first action; it is never the phase completion rule or a phase stop point.
8. A contextual successor draft preloads the old phase's complete `completion.snapshot`. Update only its final summary, evidence, and declared `completion.snapshot.phase.done_when_status`. Under `next`, provide the new summary, phase outcome, phase done criteria, first step, and only the explicit `overrides` / `changes`. Quote the user's phase authorization verbatim. The CLI clears `authority.must_not` for the new phase; declare the next holder's boundary under `next.overrides.authority.must_not` when needed. It inherits the design contract, invariants, non-goals, remaining work, references, and active decisions, initializes new criteria to `pending`, and creates the predecessor completion summary. Never retype inherited fields merely to reconstruct the container.
9. Within one phase, treat `phase.outcome`, `phase.done_when`, `design.invariants`, and `design.non_goals` as protected acceptance criteria. **Text equality is exact**: appending a suffix, including “deprecated”, “not applicable”, or an exception, is a replacement rather than preservation. Every replacement must be explicit in `changes.criteria`. Use `strengthened` only for a genuine tightening of phase outcome, phase done criteria, or invariants; provide the exact old text, exact replacement, reason, and `authorized_by: null`. Use `removed`, `weakened`, or `merged_into` only after explicit user authorization. Every new list item requires `added`; positive criteria use `authorized_by: null`, while **Adding `design.non_goals` shrinks scope** and requires explicit user authorization. Never use `strengthened` for a non-goal or invent authorization. A successor's new phase outcome and done criteria are a fresh phase contract, but its inherited invariants and non-goals remain protected. Each accepted transition becomes a complete `criteria_changes` receipt with a revision-local `ordinal` starting at 1; `delta.criteria_changes` returns that complete receipt, and historical lookup uses relay id + revision + ordinal. `strengthened` is the writer's declaration, not semantic proof by the CLI.
10. Keep every active decision's full details in the current `snapshot.decisions`; for successor changes to those details, use `next.overrides.decisions`. In every `changes.active_decision_ids`, list every ID that must remain active at the end of that operation. A missing, extra, duplicate, or exited ID is rejected, so **never delete an active decision by omission**. `changes.decisions` is only for explicit retire/supersede lifecycle transitions with reason and a valid replacement when superseding. Never reuse retired IDs or silently rewrite a locked decision.
11. Keep only current truth and **整份重写** a same-phase snapshot; write only the contextual successor fields for a phase advance. Never append chat history, timelines, changelogs, old revisions, full diffs, logs, or source. Canonical JSON is authoritative and Markdown is a derived export. Never edit either formal file. If the export is missing, modified, invalid, or oversized, load reports non-blocking `document_export` diagnostics and renders from canonical. If the user identifies the active baton itself as erroneous, run `relay draft create --operation withdraw --relay-id <internal-relay-id>`, fill `payload.reason`, validate it, and execute `relay withdraw --request <internal-file>`; do not disguise it as a completed phase with `done`.
12. Run `relay validate --request <internal-file>` for every operation before applying it.
    - **Hard limits, preflighted on every write.** Request input **96 KiB**; final canonical JSON, derived Markdown, and complete load response each use the single 128 KiB total hard limit.
    - **What lives where.** The current canonical carries every active decision in full. Load returns the same complete set in `active_decisions`; there is no current-format active-decision cold registry.
    - **Never trade content for a limit.** Never omit per-criterion completion status, active decisions, invariants, phase completion criteria, P0, escalation, security, or failure handling to fit a limit, and never rely on silent load truncation.
    - **Soft budgets require one refinement pass.** When the response carries the single `budget_advice` field because the complete response exceeds the 48 KiB soft budget, refine the heaviest top-level fields it names, then re-run `validate`.
    - **What refinement may remove.** Narration of the work sequence, timelines, restated conclusions, log dumps, and pasted source — **never** the four decision elements, per-criterion completion status, or still-binding constraints.
    - **When `active_decisions` dominates**, `supersede` / `retire` decisions that no longer bind future work; shrinking prose does nothing for it.
    - **If it still exceeds the soft budget**, state in the handoff why the heaviest sections cannot shrink further and continue without asking the user. A raised hard limit is not permission to write loosely.
13. Create or update with `relay pass --request <internal-file> --client <WRITER_IDENTITY> --model <current-model>`. Advance with `relay successor --request <internal-file> --client <WRITER_IDENTITY> --model <current-model>`; one CAS archives the old record and creates the new record. The request's `target` envelope already carries relay id and expected revision, so never append target arguments to these commands. `<WRITER_IDENTITY>` is an installation placeholder, never a literal runtime value. The installation model must replace every occurrence with the user-confirmed stable writer identity; never substitute the host adapter name such as `codex` or `claude-code`.
14. If the user explicitly requests a model switch before phase completion, update the same active Relay so the next model can load it. If the user defines the next phase, use the successor transaction rather than standalone `done` followed by manual reconstruction. Never make the user copy audit/review prose between models. Stop on `stale_revision`, store divergence/dirty state, `request_too_large`, `load_too_large`, `phase_authorization_required`, secret detection, or canonical corruption; never silently truncate current truth. A Markdown export diagnostic is not canonical corruption.
15. Report phase outcome, new revision, and sync state; for a successor report both the archived predecessor and the new active pointer. On `sync_error` with `details.local_committed=true`, use the returned recovery pointers and never retry the old revision. In finally semantics run `relay draft cleanup --path <internal-file>` on **every exit path**; never delete the formal Relay file pair.
