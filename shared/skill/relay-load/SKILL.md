# Relay · 接棒

> Installation reference source. Do not copy this file verbatim. The installation model must adapt the explicit trigger, stable launcher invocation, and local client format to confirmed local facts.

Load one verified phase snapshot and align intent before implementation. Explicit invocation authorizes read/sync operations in the independent Relay store only; keep the project read-only through confirmation.

## Permission handling

- Treat the explicit entry invocation as one authorization for its complete Relay CLI, independent-store, and request-draft workflow. Never ask for approval per Relay subcommand or draft file.
- Use the host's active permissions first. Do not preemptively request elevated or full-access execution. `--help` and read-only `status` never justify proactive escalation.
- If the host actually denies a required Relay operation, stop repeated one-command requests and ask for one scoped Relay permission profile or authorization covering the stable launcher, Relay work directory, and configured remote.
- In full-access/no-approval mode, omit all escalation metadata. A permission change applies only after the current call ends and the execution environment refreshes.
- Never widen Relay authorization to project edits, project commit/push, setup, dependency installation, or unrelated configuration.

## Workflow

1. Require `relay`; run `relay status` and `relay list`. If the CLI cannot be launched, either command returns an error, or `configured=false`, stop without installing or changing configuration. In an otherwise successful status response, `installation.source_status.state=unavailable` means Relay source-version evidence is unavailable in this repository; that field alone does not block the daily workflow. It does not prove the installed rules are current or override installation errors and stale/dirty guards below.
2. With no active item, report none; use `relay history` only if the user needs completed-stage context. With one active item select it. With several show numbered title/phase/revision/client/model entries and ask only for a number.
3. Always run `relay load --relay-id <internal-relay-id>` after selection and remember its id plus expected revision. The entire response has a **128 KiB** cap with a 48 KiB soft budget; when it carries the single `budget_advice` field, note which top-level field dominates so the next handoff can refine it. If a warning with code `installation_warnings_truncated` appears, the installation diagnostics were cut to fit the response budget — run `relay status` for the full picture instead of treating the install as healthy.
4. Read the action card's **one-line status** and first action before the phase criteria, then read the structured delta. Never infer “redo the phase” from a noun-like title or from criterion text without status. Report changed paths, decision changes, every `delta.criteria_changes` entry, source changes, truncation, and `source_relation`. For `dirty_unverifiable`, complete every item in `source_verification.checklist`; for changed source, reconcile the real worktree before following the old command hint. If `warnings` contains `installation_stale`, stop before project edits and report which client adapter must be reinstalled. If it contains `installation_source_dirty`, stop and report that uncommitted Relay source prevents proving which rules are installed; require that source to be committed or cleaned before installation is assessed or updated. Inspect `document_export`: a missing, modified, invalid, or oversized Markdown export is a non-blocking diagnostic, and the response's `document` is freshly rendered from canonical JSON.
5. Require `active_decisions_complete: true` and verify that `active_decision_count` equals the number of entries in `active_decisions`. The CLI has already flattened every active decision into full text: include all of them in the receipt, stop on any missing or unresolved entry, and never call `recall` merely to understand an active decision. Also require `phase_completion.alignment_complete: true`, verify criterion/status counts, and read every `met`, `partial`, `unverifiable`, or `pending` result. Never infer `met`. Read the CLI-generated predecessor completion summary, including the previous outcome, every criterion's completion status, evidence count, and done-record pointer. Treat `status_source=legacy_inferred` and completion-status warnings as unknown historical inference, never verified truth. `delta.criteria_changes` already contains each complete receipt for the loaded revision. Use `relay recall --relay-id <source-id> --revision <source-revision> --criteria-ordinal <ordinal>` only for another current-format revision's audit history. `--criteria-id <C-NNN>` exists for legacy archive compatibility only. Recall returns one specified object without pagination; never bulk-load history. 若需查询已退出决策正文，`--revision` 必须指定仍含正文的历史版本：例如在第 N 版退出，就查询仍含正文的 N−1 版；退出发生的 N 版已没有正文，CLI 不会自动回溯。判据回执仍查其变更发生的 revision 与该版 ordinal。
6. Use one bounded `relay history` response only for stage orientation. It is not a substitute for the active snapshot.
7. Produce a structured **理解回执** covering final outcome, phase outcome, phase done criteria, non-goals, invariants, priorities, all visible active decisions, authority, assumptions, unknowns, deviations, code conflicts, source relation, exact first action, expected result, step done condition, failure branch, and phase stop point. Restate every `authority.must_not` entry as a limit on **you, this leg** — it is not a phase contract and does not carry to whoever takes the baton next. If a `must_not` entry contradicts what the user just asked you to do, say so and ask; never treat it as grounds to open a new phase.
8. State the maintained id/revision and **等待用户明确确认**. Before confirmation do not modify project files, run destructive commands, commit, or push.
9. After confirmation, follow project instructions. **Unless the user requests a handoff, continue working until `phase.done_when`**. Completing `next_step.done_when`, an internal batch, a test gate, or an ordinary review does not complete the phase and is not a model-chosen phase stop point.
10. The only valid early stop/handoff conditions are **phase completion, a real blocker, authority escalation, or an explicit user request to switch models**. Never turn an internal batch boundary or ordinary review into user-mediated model ping-pong, offload routine review to the user, or stop merely to request another model's approval.
11. The user may redirect the work at any time. If the user explicitly requests a mid-phase model switch, use the installed Relay handoff entry to write the same active phase's current truth; never ask the user to copy audit or review text between models. Do not choose or invoke another model or external service automatically. Never edit canonical JSON or derived Markdown directly.
